# datadam

[![CI](https://github.com/anlohse/datadam/actions/workflows/ci.yml/badge.svg)](https://github.com/anlohse/datadam/actions/workflows/ci.yml)

A persistent key-value store compatible with the **Redis (RESP2/RESP3)** and **memcache (text)** protocols.
RocksDB is the source of truth on disk, and an **object cache on a memory pool of its own** sits in front of
it. The long-term goal is to offer Redis-style data structures with **persistent secondary indexes** (see the
roadmap).

**Full documentation for users and developers: [docs/](docs/README.md).**

## Building

Requirements: CMake ≥ 3.25, a C++20 compiler (MSVC 2022+/GCC 13+/Clang 17+) and [vcpkg](https://vcpkg.io).
The dependencies (RocksDB, Asio, OpenSSL, nlohmann-json, LuaJIT, GoogleTest) are installed by vcpkg from
`vcpkg.json`.

**Windows** (in an "x64 Native Tools Command Prompt", or by opening the folder in Visual Studio):

```bat
set VCPKG_ROOT=D:\cpp\vcpkg
cmake --preset windows
cmake --build --preset windows-release
ctest --preset windows-release
```

**Linux:**

```bash
export VCPKG_ROOT=~/vcpkg
cmake --preset linux && cmake --build --preset linux -j && ctest --preset linux
```

**Docker (Linux):** the [Dockerfile](Dockerfile) builds with GCC 13 on Ubuntu 24.04, using the same vcpkg
commit as the manifest. The dependencies live in a layer of their own, rebuilt only when `vcpkg.json`
changes.

```bash
docker build --target test -t datadam:test .   # builds and runs the unit tests and the integration test
docker build -t datadam .                      # slim image, with the binary only
docker run -d -p 6379:6379 -p 11211:11211 -v datadam-data:/var/lib/datadam datadam
```

CI publishes the image of every commit on `main` that passes all the tests:
`docker pull ghcr.io/anlohse/datadam:latest` (or `:sha-<commit>`).

`tests/run_integration.sh` starts a fresh server and runs `tests/integration_test.py`. Then it kills the
process with `kill -9`, starts the server again, checks that the data persisted, and tests a clean shutdown
with SIGTERM.

If the network or an antivirus intercepts HTTPS (Avast does, for example), the build cannot download the
dependencies. In that case, pass the interceptor's root certificate as a secret:
`docker build --secret id=extra_ca,src=root.crt ...`. The certificate is used in the build stages only and
never reaches the final image.

**Tests with the official redis-cli:** the script below starts the image and runs the tests from the
`redis-cli` of the `redis:7.4` image. There are 649 checks covering every command, error cases included,
followed by two persistence cycles: write → `docker stop` → start → check, and write → `docker kill -s KILL` →
start → check. Then the suite runs again over TLS, and a replica starts in another container to check the full
sync, the write stream, `READONLY` and promotion.

```bash
bash tests/docker_redis_cli.sh            # or: tests/redis_cli_test.sh <host> <port> commands|write|verify
```

## Running

```bash
build/windows/Release/datadam datadam.conf
build/windows/Release/datadam datadam.conf --port 6380 --cache-max-memory 1gb
```

Any option of `datadam.conf` can also be given as `--option value` on the command line.

**Changing settings while the server runs** (`CONFIG SET`, several pairs at once; either all apply or none
does): `log-level`, `fsync`, `write-batching`, `cache-min-memory`, `cache-max-idle`, `cache-max-age`,
`cache-on-write`, `cache-admission`, `rocksdb-block-cache`, `rocksdb-write-buffer`, `requirepass`,
`acllog-max-len`, `masteruser`, `masterauth`, `backup-dir`, `backup-keep`, `slowlog-log-slower-than`,
`slowlog-max-len` and the `tls-*` options (except the port). The other options (port, directory, memory pool
size...) change only with a restart, and `CONFIG SET` replies `can't set immutable config`.

**`CONFIG REWRITE`** writes the current settings and the ACL users into the file the server started with.
Each option already in the file gets its current value on the same line; comments, blank lines and order stay
as they are. What was not in the file and differs from the default goes at the end, under
`# Generated by CONFIG REWRITE`, together with the `user` lines. The new file is written next to the old one
and renamed over it, so a crash halfway never leaves half a file. Without a configuration file, the command
replies an error. In the Docker image the server owns `/etc/datadam`, so the rewrite works; to keep it when
the container is recreated, mount the file in a volume.

**Protected mode.** As in Redis, while the `default` user has no password, only clients on the loopback
interface may connect (`protected-mode yes`, the default); others get `DENIED` and the ways out. The Docker
image turns it off, as Redis's does, since a container's ports are reachable only where they are published.

**Password.** With `requirepass` (in the file or through `CONFIG SET`), every new connection needs
`AUTH <password>` (or `AUTH default <password>`, or `HELLO 3 AUTH default <password>`) before any other
command; before that only `AUTH`, `HELLO` and `QUIT` are accepted, and requests larger than 16 KB close the
connection. Connections already authenticated stay valid when the password changes. A wrong password replies
`WRONGPASS` and counts in `auth_failures` (`INFO stats`). On memcache, whose text protocol has no
authentication, the connection must send `auth [user] <password>` first. With redis-cli:
`REDISCLI_AUTH=<password> redis-cli ...`.

**Users (ACL).** The rules are Redis's: `requirepass` is the password of the `default` user, and other users
are created with `ACL SETUSER` (or with `user <name> <rules>` lines in the configuration file).

```
ACL SETUSER app on >s3cret ~app:* %R~shared:* +@read +@write -@dangerous
ACL SETUSER ops on >pw allkeys +@all -config +config|get
ACL GETUSER app / ACL LIST / ACL USERS / ACL DELUSER app / ACL CAT [category] / ACL WHOAMI
AUTH app s3cret          # or: REDISCLI_AUTH=s3cret redis-cli --user app
```

- **Commands.** `+cmd` and `-cmd`, subcommands (`+config|get`), categories (`+@read`, `-@dangerous`; `ACL CAT`
  lists them all, including datadam's own `@index`), `allcommands` and `nocommands`. Rules apply in the order
  they appear, as in Redis.
- **Keys.** `~pattern` grants read and write, `%R~pattern` read only and `%W~pattern` write only; `allkeys`
  is `~*`. Each command knows which arguments are keys and whether it reads or writes them: in `SINTERSTORE`,
  for example, the destination needs write access and the sources read access. A key without permission
  replies `NOPERM No permissions to access a key`; a command without permission, `NOPERM User app has no
  permissions to run the 'del' command`.
- **Commands that return keys.** `KEYS`, `SCAN`, `IDX.QUERY`, `IDX.GET` and `IDX.COUNT` show and count only
  the keys the user may read. Redis returns them all; here a user limited to `~app:*` does not discover keys
  with other prefixes.
- **Passwords.** They are stored as SHA-256 (`>password`, `#hash`, `<password`, `!hash`, `nopass`,
  `resetpass`). An `off` user cannot log in, but connections already open go on.
- **Changes take effect at once.** Changing a user's permissions applies from the next command of the
  connections already open. Deleting a user closes its connections.
- **memcache.** A memcache connection logged in as a user has the permissions of the equivalent Redis
  commands: `get` needs `mget`, `set` needs `set`, `delete` needs `del` and so on, with the keys always
  checked.
- **Cost.** For a user with full access, the common case, the check costs one atomic read per command. For a
  restricted user, it is a few bits and one glob match per key. In a redis-benchmark run with a pipeline of 16
  there was no measurable difference.
- **ACL LOG.** Keeps the refusals (`reason` `command` or `key`) and the failed logins (`auth`), newest first,
  with the user, the refused object and the connection's `client-info`. Repeats of the same refusal within a
  minute add to the `count` of the same entry. It accepts `ACL LOG <n>` and `ACL LOG RESET`; the maximum size
  comes from `acllog-max-len` (128 by default, changeable with `CONFIG SET`). Refusals and failures on
  memcache are logged too. `INFO stats` shows `acl_access_denied` and `auth_failures`.
- **Limits.** There are no selectors, no `ACL SAVE/LOAD` and no separate ACL file yet.

**TLS.** An optional TLS port for the Redis protocol, next to the plain port (or alone, with `port 0`):

```
tls-port 6380
tls-cert-file /etc/datadam/server.crt      # the server's chain (PEM)
tls-key-file /etc/datadam/server.key
tls-ca-cert-file /etc/datadam/ca.crt       # CAs that sign client certificates
tls-auth-clients yes                       # yes (default, as in Redis) | optional | no
tls-auth-clients-user cn                   # the certificate's CN logs in as the ACL user of that name
tls-protocols TLSv1.2,TLSv1.3
```

```bash
redis-cli -p 6380 --tls --cacert ca.crt --cert client.crt --key client.key PING
```

- **Client certificates.** `tls-auth-clients yes` requires the client to present a certificate signed by a CA
  of `tls-ca-cert-file`; with `optional` the certificate is verified only if the client sends one; with `no`
  none is asked for.
- **Login by certificate.** With `tls-auth-clients-user cn`, a valid certificate logs in directly as the ACL
  user whose name is the CN, without a password. If that user does not exist or is `off`, the normal rule
  applies, and the client can still use `AUTH`.
- **Changing certificates.** `CONFIG SET tls-cert-file ...` (and the other `tls-*` options, except the port)
  loads a new context for the next connections; the open ones keep the old one. If a file does not load, the
  `CONFIG SET` fails and nothing changes: this is how a certificate is renewed without a restart. The files
  are read again even with the same path, so it is enough to overwrite them and repeat the `CONFIG SET`.
- **Protections.** A handshake that does not finish within 10 s closes the connection. `CLIENT INFO` and the
  `client-info` of `ACL LOG` show `tls=yes`, and `INFO stats` shows `tls_connections` and
  `tls_handshake_failures`.
- **Cost.** Measured with redis-benchmark, 50 clients, in thousands of requests per second:

  | | No pipeline | Pipeline 16 |
  |---|---|---|
  | SET / GET without TLS | 150 / 154 | 995 / 2,061 |
  | SET / GET with TLS | 111 / 109 | 719 / 1,273 |

- **Limits.** memcache stays plain text only. TLS uses OpenSSL (through vcpkg).
- **Tests.** The redis-cli test runs the whole command suite over TLS, with a client certificate. There are
  also end-to-end C++ tests that generate a CA and certificates and start a real server. On a machine whose
  antivirus intercepts TLS even on 127.0.0.1 (Avast does), these tests detect the interception and are
  skipped with the reason; in Docker they run.

**SCAN.** `SCAN`, `HSCAN`, `SSCAN` and `ZSCAN` accept `MATCH`, `COUNT` (how many keys or elements to look at
per call), `TYPE` on `SCAN` and `NOVALUES` on `HSCAN`. Since keys and elements are kept in order in RocksDB,
each call continues right after the last item returned: everything that existed during the whole iteration
shows up exactly once, never repeated (Redis only guarantees "at least once"). A `MATCH` that starts with
fixed text (`user:*`) walks only the keys with that prefix. Clients expect numeric cursors, so each cursor is
a number that points to a position kept on the server; the 100,000 most recent are kept, and any connection
can continue any cursor.

```bash
redis-cli -p 6379 set user:1 ana
printf 'get user:1\r\n' | nc localhost 11211     # the same key, through memcache
python tests/integration_test.py                  # end-to-end test (uses the standard library only)
```

## Architecture

```
 RESP clients :6379 / memcache :11211
        │
 Server (Asio, C++20 coroutines, io-threads threads)
        │  RespParser / MemcacheSession  →  commands
        │  ReadPool (read-threads threads): loads from disk the keys missing
        │      from the cache for GET/MGET/EXISTS..., off the I/O threads
        ▼
 Database  ── per-key locks (4096 stripes): writes and reads that miss
        │      hold the stripe across disk + cache, so the cache never
        │      receives a stale value
        ├── ObjectCache (write-through) ── memory pool (slab)
        └── RocksStorage ── RocksDB: meta / data / index CFs, WAL, bloom filters,
                            LZ4 + ZSTD, compaction filter that drops expired keys
```

### Memory pool and cache

- **PageArena.** Reserves at once a contiguous block of addresses the size of `cache-max-memory`
  (`VirtualAlloc` with `MEM_RESERVE` on Windows, `mmap` with `MAP_NORESERVE` on Linux). The block is split
  into pages (64 KB by default), which get physical memory only when used. Freed pages go back to the
  operating system, except up to `cache-min-memory`, which stays allocated for reuse.
- **SlabAllocator** (one per shard). Each page is dedicated to a size class (a geometric progression ×1.25,
  from 88 B up to `72 + cache-max-object-size`) and split into equal chunks. Allocation uses a free list per
  page and is O(1). When a page becomes empty, it goes back to the arena and can serve any class or shard.
- **ObjectCache.** It has 16 shards, each with its own mutex, intrusive hash table and one LRU per class. The
  object (72 B header + key + value) lives inside the chunk, and `GET` replies straight from the pool's
  memory, with no intermediate copy.
- **Objects larger than `cache-max-object-size`** (4 KB by default) never enter the pool: they are read from
  RocksDB, which has a block cache of its own (`rocksdb-block-cache`).

Eviction policies:

| Situation | What leaves |
|---|---|
| Pool full | The item unused for the longest time (LRU). If the oldest item belongs to another size class, its whole page is emptied and reused (*page steal*). |
| Pool full and a new key (`cache-admission yes`) | Nothing: the key enters only on its second access within a short window (see below). |
| `cache-max-idle` | Items not read for that long, never going below `cache-min-memory`. |
| `cache-max-age` | Items loaded longer ago than that, even if they are hot. |
| Key TTL | Expired items leave on read or in the periodic sweep. |

**Admission filter.** With the pool full, a pure LRU lets every one-off write or read evict an item, even if
that key is never asked for again. A bulk load or a write of cold keys replaces the whole cache with whatever
passed last. The filter is TinyLFU's *doorkeeper*: two generations of a Bloom filter (about 8 bits per key)
remember the keys seen recently. While there is room, everything enters. With the pool full, a key that is not
in the cache yet enters only if it had already shown up in the window, that is, on its second access. A key
already in the cache is always updated, and a key the read pool loaded for a client waiting for it always
enters. The `rejected_admission` counter (`CACHE STATS`, `INFO cache`) shows how many were left out, and
`cache-admission no` turns the filter off.

The `CACHE STATS`, `CACHE CLASSES` (pages and items per size class) and `INFO cache` commands show how the
cache behaves. `CACHE CLEAR` empties the cache without deleting data.

### Collections (Hash, Set, ZSet, List)

A collection is a record in the `meta` CF, with its type, TTL and a 24-byte `CollectionMeta` (version, size
and, for lists, the head position), plus one entry per element in the `data` CF:

```
data:  u32 key length | key | u64 version | subkey        (big-endian integers)
  hash   subkey = field                     value = the field's value
  set    subkey = member                    value = ""
  zset   'm' + member                       value = score (8 sortable bytes)
         's' + sortable score + member      value = ""       (index by score)
  list   u64 (head + i)                     value = element  (push at both ends in O(1))
```

- **Version.** Every new collection gets a new version that is never reused, not even after a restart,
  because a mark persisted in the default CF always stays ahead of the last version used. That is why `DEL`,
  `EXPIRE` or `SET` over a collection are O(1): the old version's elements become invisible at once.
- **Cleanup.** The old version's elements go away through a `DeleteRange` in the same batch (on `DEL` and on
  an expiry noticed by a read) or, if nobody removed them explicitly (a blind `SET` over it, a TTL that ran out
  without a read), through the `data` CF's compaction filter, which drops elements whose version is not the
  current record's.
- **Atomicity.** Each command runs in a transaction on its key (`Database::transact`). It sees its own writes
  and the pipeline's (an ordered overlay over RocksDB, in scans too), and is undone entirely if it fails
  halfway. Multi-key commands (`SMOVE`, `SINTERSTORE`, `LMOVE`...) lock all their keys in ascending stripe
  order.
- **Small collections in the cache.** Collections of up to 128 elements that fit in a cache object
  (`cache-max-object-size`) are kept whole in the cache: the `meta` record carries all the elements, encoded in
  order (`ElementSet`, read in its own buffer, with no allocation per element). Reads (`HGET`, `HGETALL`,
  `SMEMBERS`, `ZRANGE`, `LRANGE`...) are served straight from the cache, without the key lock, like `GET`.
  Writes change the elements in memory, and in a pipeline they pass from one command to the next without going
  back to the cache. The new version goes to the cache only when the batch is written, so lock-free readers
  never see unwritten elements. Larger collections keep only the `meta` in the cache (so `HLEN`, `TYPE` and
  `TTL` do not touch the disk either) and read their elements from RocksDB.
- **Costs.** `ZRANK`, `ZRANGE` by position, `LINSERT` and `LREM` walk up to the requested position (O(N)), as
  in Kvrocks.

### JSON type

JSON documents with the RedisJSON commands:

```
JSON.SET user:1 $ '{"name":"ana","tags":["a","b"],"address":{"city":"SP"}}'
JSON.GET user:1 $.address.city                  # ["SP"]
JSON.GET user:1 .address.city                   # "SP" (legacy path: a single value)
JSON.SET user:1 $.age 30                        # creates the member, if the object exists
JSON.NUMINCRBY user:1 $.age 1                   # [31]
JSON.ARRAPPEND user:1 $.tags '"c"'              # [3]
JSON.GET orders $..items[?(@.price > 10 && @.sku != "x")].sku
JSON.MERGE user:1 $ '{"address":null,"vip":true}'   # merge patch (RFC 7386)
```

- **Paths.** Both RedisJSON syntaxes work.
  - JSONPath: `$`, `.name`, `['name']`, `[0]`, `[-1]`, `.*`, `[*]`, `..` (at any depth), slices `[1:3]` /
    `[::-1]`, unions `[0,2]` and filters `?(...)` with `== != < <= > >=`, `&&`, `||`, `!`, existence
    (`?(@.isbn)`) and paths from the root (`$...`) inside the filter.
  - Legacy (`.a.b[0]`, `a.b`, `.`): selects a single value. The command replies with it, or with an error if
    the path does not exist.
  - With `$`, the command acts on every value found and replies one result per value (nil where the type does
    not fit). Without a path, the legacy root `.` applies.
- **Storage.** A document is a record like a string (type `ReJSON-RL` in `TYPE`), stored as compact JSON
  text. Every write reads the document, changes it and writes it whole, under the key lock. That is why `DEL`,
  `EXPIRE`, `RENAME`, `SCAN ... TYPE ReJSON-RL`, the object cache, the change feed (operation `json`) and
  replication already work for JSON. Objects keep the insertion order of their keys, and integers stay
  integers. Documents nest up to 128 levels, as in RedisJSON.
- **Reads.** `JSON.GET` without a path returns the stored text without decoding the document. Reads
  (`JSON.GET`, `MGET`, `TYPE`, `STRLEN`, `ARRLEN`, `ARRINDEX`, `OBJKEYS`, `OBJLEN`) that miss the cache go to the
  read pool, like `GET`.
- **Cost.** With a ~40-byte document and 100 connections: `JSON.SET` 292k/s (`SET` with the same text:
  312k/s); `JSON.GET` of the whole document 470k/s, the same as `GET`; `JSON.GET $.age` 451k/s;
  `JSON.NUMINCRBY` 304k/s. Large documents cost in proportion to their size on every write.
- **Indexes.** JSON documents can have secondary indexes (`IDX.CREATE ... ON JSON`, see below).
- **Not yet.** `JSON.RESP`, `JSON.DEBUG` and filters with regular expressions (`=~`).

### Secondary indexes on Hash and JSON

The feature Redis lacks: querying hashes (or JSON documents, further down) by the value of their fields,
without maintaining indexes by hand.

```
IDX.CREATE users PREFIX 1 user: SCHEMA city TAG age NUMERIC        # compound index (city, age)
IDX.CREATE emails PREFIX 1 user: SCHEMA email TAG UNIQUE

HSET user:1 name ana city SP age 30 email ana@x                     # the index maintains itself
IDX.QUERY users city = SP age >= 18 age < 30 LIMIT 0 10             # key + fields of each hash
IDX.QUERY users city = SP name = ana RETURN 1 email                 # name filters what the index found
IDX.QUERY users city = SP DESC NOCONTENT                            # keys only, in descending order
IDX.COUNT users city = SP
IDX.GET emails ana@x                                                # exact lookup (one value per field)
IDX.INFO users / IDX.LIST / IDX.DROP users
```

- **Model.** Each index covers the hashes whose keys start with one of its prefixes (or all of them, without
  `PREFIX`) and has up to 8 fields, `TAG` (exact text) or `NUMERIC`. As in a relational database's compound
  index, equality on the first fields plus a range (`> >= < <=`) on the next one become a single sequential
  read. Any other condition, on an index field or not, filters the hashes found. Results come in index order,
  and the default `LIMIT` is 10. A hash missing one of the fields (or with a `NUMERIC` that is not a number)
  stays out of the index.
- **Several values.** A `TAG` with a `SEPARATOR` (`SCHEMA skills TAG SEPARATOR , level NUMERIC`) keeps each
  piece as a value (`"c++, go"` becomes `c++` and `go`, with no spaces at the ends), and the same goes for
  arrays in JSON. The key gets one entry per combination of values, up to 1,024 (beyond that, it stays out of
  the index). `skills = go` finds whoever has `go` among their skills, two conditions on the same field
  require both values, and a key appears only once in the results and in the count.
- **Format.** In the `index` CF: `u32 index id | value of each field | key`, and the entry's value keeps the
  hash's version and its TTL. Values are encoded preserving order: `NUMERIC` in 8 sortable bytes and `TAG`
  with escaping and a terminator. In `UNIQUE` indexes the key goes in the entry's value, so "does this value
  already exist?" is a point read.
- **Consistency.** The entries are written in the same WriteBatch as the hash on every write that touches it
  (`HSET`, `HDEL`, `HINCRBY`, `DEL`, `EXPIRE`, `PERSIST`, `RENAME`, and also blind `SET`/`MSET` over a hash),
  so the index and the data never diverge in a crash. Since the entry carries the version and the TTL, it is
  valid without reading the hash: `IDX.COUNT` and `IDX.QUERY ... NOCONTENT` read only the index. When the query
  needs the fields (content, `RETURN` or filters), it reads from a RocksDB snapshot and checks the version and
  the values. An entry that does not match is skipped and repaired on the spot, and the `index` CF's
  compaction filter drops the entries of hashes that no longer exist at that version and of dropped indexes.
- **UNIQUE.** A writer to a `UNIQUE` index takes its lock and writes before releasing it, so two connections
  can never get the same value (a test has 8 threads competing for the same e-mail). A violation undoes the
  whole command and replies `ERR UNIQUE index 'emails' already has this value, for key 'user:1'`.
- **Backfill.** `IDX.CREATE` registers the index (from then on every write maintains it) and scans the
  existing hashes in the background. Meanwhile its state is `building` and `IDX.QUERY` refuses queries. If a
  `UNIQUE` index finds repeated values in the data, it becomes `failed`, with the reason in `IDX.INFO`. The
  definition is kept in the system CF and survives restarts; an interrupted backfill starts again on its own.

Measured costs (Docker, 100,000 hashes, 50 clients):

| Operation | thousands/s |
|---|---|
| `HSET` through `--pipe`, no index / 1 index / + 1 `UNIQUE` | 224 / 170 / 126 |
| `IDX.GET` on a `UNIQUE` index, no pipeline / pipeline 16 | 139 / 641 |
| `IDX.QUERY city = c42 age < 30 LIMIT 0 10`, no pipeline / pipeline 16 | 92 / 158 |
| `IDX.QUERY city = c42 LIMIT 0 100 NOCONTENT` | 95 |
| `IDX.COUNT` over 1,000 hashes | 41 (was 1.8 when checking each hash) |

`UNIQUE` costs more because each write to it is written at once, instead of waiting for the rest of the
pipeline.

**On JSON documents.** The same index, with paths instead of fields:

```
IDX.CREATE users ON JSON PREFIX 1 user: SCHEMA $.address.city AS city TAG $.age AS age NUMERIC
IDX.CREATE emails ON JSON PREFIX 1 acct: SCHEMA $.email TAG UNIQUE        # without AS: the name is the path

IDX.QUERY users city = SP age > 35                  # key + ["$", document]
IDX.QUERY users city = SP $.name = ana NOCONTENT    # conditions on other paths filter the results
IDX.QUERY users city = SP RETURN 2 age $.name
```

- **A field's value.** It is the values the path finds in the document: a string counts as it is, and a
  number or boolean counts by its JSON text. An array counts by each element (`$.tags` with `["db","cpp"]`
  finds the document by `db` and by `cpp`), as does a path that matches several times (`$.items[*].sku`).
  Nulls and objects are ignored. If no value is left, the document stays out of the index, like a hash without
  the field.
- **Maintenance.** The entries change in the same batch as the document, on every write that touches it: the
  `JSON.*` commands; `SET`, `MSET` or memcache writing over it; a collection command that replaces the
  document; `DEL`, `EXPIRE`/`PERSIST` and `RENAME`. Backfill, `UNIQUE` (with the same lock and the same
  immediate commit) and repairing entries during queries work as for hashes.
- **Validity.** A document has no collection version. Since every write rewrites its entries, a query that
  reads the document checks the entry against it, and the compaction filter drops entries whose owner is gone,
  expired or is no longer JSON.
- **Cost** (~40-byte document, 100,000 keys, 100 connections): `JSON.SET` does 315k/s without an index and
  289k/s with a two-field index; `JSON.NUMINCRBY` on an indexed field, 213k/s; `IDX.QUERY city = SP
  LIMIT 0 10` returning the documents, 106k/s.

### RediSearch-compatible search (`FT.*`)

The `FT.*` commands of RediSearch (and Kvrocks) for `TAG` and `NUMERIC` fields, over hashes or JSON
documents. Clients that already speak this syntax work unchanged.

```
FT.CREATE items ON HASH PREFIX 1 item: SCHEMA color TAG price NUMERIC SORTABLE size AS sz TAG CASESENSITIVE
FT.CREATE docs ON JSON PREFIX 1 doc: SCHEMA $.tags[*] AS tag TAG $.score AS score NUMERIC

FT.SEARCH items "@color:{red | blue} @price:[10 (50]" SORTBY price DESC LIMIT 0 10
FT.SEARCH items "@color:{gr*} -@sz:{M}" NOCONTENT          # prefix, negation
FT.SEARCH items "@price:[$lo $hi]" PARAMS 4 lo 10 hi 20 DIALECT 2
FT.SEARCH docs "*" RETURN 3 $.name AS name score LIMIT 0 0  # LIMIT 0 0: the total only
FT.INFO items / FT._LIST / FT.TAGVALS items color / FT.DROPINDEX items [DD]
```

- **How it differs from `IDX.*`.** An `FT` index indexes each field separately. A document missing a field
  stays in the index (it shows up in `*` and in queries on the other fields), and a query combines any fields.
  In the `index` CF, each value of each field becomes an entry `id | field position | value | key`, and each
  document has one more presence entry. Version, TTL, maintenance in the same batch, backfill and the
  compaction filter are the same as for `IDX.*`.
- **Queries.** There are `@field:{a | b | pre*}`, `@field:[min max]` (with `(` for an open bound and
  `-inf`/`+inf`), intersection by juxtaposition, union with `|` (which binds tighter than intersection, as in
  RediSearch), negation with `-`, parentheses, `*` and `$parameter`. The query becomes set operations on the
  keys that index reads find, without reading any document. Only the page returned is read, from a snapshot.
  The total (the first item of the reply) counts every result. Without `SORTBY` the order is the keys'. With
  `SORTBY` the order follows the field's index and stops as soon as the page is full; documents without the
  field go last.
- **TAG.** On a hash, the default separator is `,`. In JSON there is no default separator: an array gives one
  value per element. Values ignore case unless the field is `CASESENSITIVE`, and the content returned is the
  original.
- **Options.** `NOCONTENT`, `RETURN` (with `AS`), `SORTBY`, `LIMIT`, `PARAMS`, `WITHSCORES` (always 1) and
  `FILTER field min max` work; `DIALECT`, `TIMEOUT`, `VERBATIM` and the like are accepted and ignored. In
  `FT.CREATE`, `SORTABLE`, `NOINDEX`, `LANGUAGE`, `STOPWORDS` and the like are also accepted and ignored, and
  `SKIPINITIALSCAN` skips the backfill. While the backfill runs, `FT.SEARCH` replies with what has been
  indexed so far, as in RediSearch.
- **Not supported.** `TEXT` (full-text search), `GEO` and `VECTOR` fields, `FT.AGGREGATE`, aliases,
  `FT.ALTER` and `FT.EXPLAIN`. `FT.CREATE` refuses these field types with an error, instead of creating an
  index that does not answer.

Measured costs (Docker, redis-benchmark with 50 connections; for the queries, 100,000 hashes with 100 colors,
1,000 prices and 10 sizes):

| Operation | thousands/s |
|---|---|
| `HSET` of 3 fields with new values, no index / 3-field `FT` index / 2-field compound `IDX` | 222 / 111 / 100 |
| `FT.SEARCH "@color:{c42}" LIMIT 0 10` (1,000 results, returns 10 hashes) | 33 |
| the same with `NOCONTENT` | 40 |
| `FT.SEARCH "@color:{c42} @price:[0 99]"` (intersection of 1,000 with 10,000) | 3.9 |
| `FT.SEARCH "@price:[0 99]" SORTBY price LIMIT 0 10` (10,000 results) | 3.2 |
| `FT.SEARCH "*" LIMIT 0 0` (counts 100,000) | 0.9 |
| `IDX.QUERY color = c42 price < 100 LIMIT 0 10`, on the compound index | 80 |

`FT.SEARCH` always computes the total, so it pays for every entry of each field in the query. For a
combination of fields that is queried all the time, a compound `IDX.*` index over the same data reads only the
page's slice and is 20× faster. Both kinds of index can live on the same prefix.

### Small, hot collections: before and after the element cache

both versions:

| Test | Without the element cache | With it |
|---|---|---|
| `ZRANGE z 0 -1` (sorted set of 20 members, scores changing) | 1 / 2 | 130 / 775 |
| `HGETALL h` (hash of 20 fields being rewritten) | 56 / 71 | 118 / 523 |
| `LRANGE l 0 -1` (10 elements) | 144 / 324 | 140 / 1,136 |
| Hot `HGET` / `SISMEMBER` / `LINDEX` | ~152 / 1,400–1,700 | ~152 / 2,000–2,150 |
| `SADD` into a set of 20 members | 151 / 1,626 | 152 / 2,127 |
| `HGETALL` over 100,000 small hashes | 148 / 651 | 146 / 1,369 |
| `HSET` over 100,000 small hashes | 156 / 458 | 157 / 560 |
| `HSET` into a hash of 20 fields | 152 / 615 | 153 / 584 |

The pathological case was reading a small collection that changes a lot: the RocksDB iterator has to skip
every old version and every tombstone of the same keys. The price of the cache shows in pure `ZADD` on a hot
sorted set: each `ZADD` changes three elements (the member and the score index), and the in-memory set is
published to the cache on every commit.

### Replication

A replica follows a primary over the Redis protocol itself and is read-only:

```
REPLICAOF 10.0.0.1 6379          # or "replicaof 10.0.0.1 6379" in datadam.conf
REPLICAOF NO ONE                 # promotes the replica to primary
ROLE / INFO replication
```

- **First sync.** The replica sends `REPLSYNC <id> <offset>`. If the primary no longer has the WAL from that
  point, or if it is the first time, it replies `+FULLSYNC` and sends a consistent snapshot of RocksDB (every
  column family, in batches of ~1 MB) read from a RocksDB snapshot. The replica deletes what it had and applies
  the batches. Meanwhile, data commands get `LOADING`.
- **Continuous stream.** Then the primary sends each WAL batch as it reached RocksDB (`wal`, with the next
  sequence), or a `ping` every second without writes. The replica writes the batch and its offset in the same
  write, and sends back `REPLCONF ACK` as soon as it applied it (`INFO replication` shows each replica's offset
  and lag).
- **Restart.** A restarted replica continues from its stored offset (`+CONTINUE`), without copying everything
  again, if the primary still keeps the WAL from that point. Otherwise, it does a full sync. If it hears nothing
  from the primary for 10 s, it reconnects.
- **On the replica.**
  - Commands that write get `READONLY` (on memcache, `SERVER_ERROR read only replica`).
  - Removing expired keys on read and backfilling indexes are left to the primary. The replica receives the
    index entries ready, and definitions created or dropped on the primary apply at once.
  - Each batch applied locks the keys it touches and removes them from the object cache, so a read never puts
    back into the cache a value older than it.
- **Promotion.** `REPLICAOF NO ONE` reloads the collections' version mark and the index definitions, resumes
  interrupted backfills and generates a new replication id. That is why other replicas of the old primary
  that start following the promoted one do a full sync.
- **Requirements and limits.**
  - The primary needs `wal-retention`, which must cover the time of a full sync. If the replica falls behind
    the kept WAL, it syncs everything again.
  - The replica authenticates with `masteruser`/`masterauth`. The user must be able to run `PING`, `REPLCONF`
    and `REPLSYNC` (which are in `@admin`).
- **`WAIT`.** `WAIT n timeout` waits, without holding a thread, until `n` replicas acknowledge the writes made
  before it. Replicas acknowledge as soon as they apply each batch, so on a good network `WAIT` returns in
  about one round trip.
- **TLS.** With `tls-replication yes`, the replica connects to the primary's TLS port, checks its certificate
  (CA and host name) and presents its own, which the primary can require and use as a login by CN.
- **`FAILOVER`.** A planned role swap that loses no write: the primary refuses new writes, waits for the
  replica to catch up, tells it in the replication stream itself, the replica becomes the primary and the old
  one starts following it (`TO host port`, `TIMEOUT`, `FORCE`, `ABORT`). It takes about 30 ms on a single
  machine.
- **Automatic failover with Redis Sentinel.** Redis 7's `redis-sentinel` works with datadam:
  `tests/docker_sentinel_test.sh` starts three sentinels, stops the primary and checks that the replica is
  promoted and that the old primary comes back as its replica. `replica-priority` sets the promotion order.
- Every change of primary makes the replicas sync everything again: offsets are positions in each primary's
  WAL, so one history does not continue on another server.

### Change feed (CDC)

With `wal-retention` greater than zero, datadam keeps RocksDB's WAL after it is no longer needed for recovery,
and `CDC.READ` returns, in order, what each committed batch changed:

```
CDC.READ 0 COUNT 100                 # from the oldest kept
CDC.READ $ BLOCK 0                   # only what is written from now on; waits with no limit
CDC.READ 1234 MATCH user:* BLOCK 5000
-> 1238                                              # sequence to continue from
   1) 1234  1761170000123  [[set user:1 ana 0]]      # batch: sequence, commit time (ms), changes
   2) 1235  1761170000150  [[meta user:2 hash 2 0 7] [hset user:2 city SP] [hset user:2 age 30]]
```

- **Changes.**
  - On records: `set key value expires_at_ms`, `del key`, `meta key type size expires_at_ms version [head]`
    (a collection's record was created or changed its size or TTL; a new version means the old content is
    gone) and `flushall`.
  - On elements: `hset`/`hdel`, `sadd`/`srem`, `zadd key score member`/`zrem` and `lset`/`ldel key position
    [value]` (position − head = index in the list).
  - Left out: secondary index entries, which are derived, and expirations done by compaction, which do not go
    through the WAL; that is why `set` and `meta` carry `expires_at_ms`.
- **How it works.** Each change comes from decoding the WAL (`GetUpdatesSince`). A collection element does
  not say in the WAL whether it is a hash field or a set member, so each batch carries a note that exists only
  in the WAL (`PutLogData`) with the commit time and the type of each collection touched. Elements of a
  version deleted in the same batch do not show up. A batch is always returned whole: `COUNT` (100 by default)
  is reached with complete batches.
- **Cursor.** The reply carries the sequence to continue from. A sequence that has left the kept WAL is an
  error (`sequence N is no longer in the kept WAL`): the consumer must start again from a snapshot.
- **BLOCK.** With nothing new, `BLOCK ms` (0 = no limit) waits for the next write without holding an I/O
  thread, like `XREAD`, and `$` is resolved only once, on the first try.
- **Retention.** The kept WAL is as large as what was written. RocksDB checks `WAL_size_limit_MB` only every 10
  minutes, so datadam itself deletes the oldest files every second to respect `wal-retention-size` (1 GB by
  default). `CDC.INFO` shows `first_sequence`, `last_sequence` and `wal_bytes`.
- **Permissions.** `CDC.READ` is in `@admin` and `@dangerous`, because it shows the value of any key. For a
  user with key patterns, only the changes of the keys it may read show up.
- **Cost.** With pure pipelined writes (1 M keys, 100 connections), the feed on did 568k and 570k writes per
  second, against 607k to 625k with it off: about 7%. The first run with it on did 401k; it was probably
  Docker's virtual disk growing to hold the first 1 GB of WAL.

### Durability

`fsync always` fsyncs on every write. `fsync everysec` (the default) fsyncs the WAL once per second: a process
crash loses nothing, and a power failure loses at most about 1 s. `fsync no` leaves the decision to the
operating system.

**Group commit per pipeline** (`write-batching yes`, the default). The writes of all the commands read at once
from a connection go to RocksDB in a single WriteBatch, written before any reply goes out. Durability is the
same as with individual writes: the client gets `OK` only after the WAL was written. Until the batch is
written, the lock stripes of the keys written stay held, so another client never reads the old value from
disk. A batch never waits for a lock while holding others: if the lock is taken, it writes what it has and
only then waits, which is why there is no deadlock. A batch also does not hold locks while the disk works. A
read that misses the cache locks the key only during its own read, without joining the batch, and writes the
batch before going to disk. A command that reads and writes a key that is not cached (`INCR`, `HSET`...) writes
the batch before locking it. `MSET`, `RENAME`, `FLUSHALL` and `KEYS` write the pending batch before they run.
`INFO persistence` shows `write_batches`, `write_batch_ops` and `write_batch_conflicts`. If a pipeline writes
the same key several times, only the last write goes to RocksDB: 16 `INCR`s on a counter become a single put.

Key locks spin briefly (`spin_try_lock`) before sleeping on the mutex, because a lock is held for
microseconds and waking a thread through the kernel costs more than that. With 50 clients running `INCR` on a
single counter, this took throughput from 92k/s to 150k/s without a pipeline, and from 718k/s to 2 million/s
with a pipeline of 16 (Redis with AOF did 159k/s and 1.4 million/s in the same test).

### Reads that go to disk

When the data does not fit in the cache, most reads go to RocksDB, and a disk read takes from hundreds of
microseconds to milliseconds. If the I/O thread waited for the disk, only `io-threads` reads would progress at
the same time, and every connection of that thread would stall with it. That is why these reads leave the I/O
threads:

- **Deferred reads.** `GET`, `MGET`, `EXISTS`, `STRLEN`, `GETRANGE`, `SUBSTR`, `TYPE`, `TTL`, `PTTL`,
  `EXPIRETIME` and `PEXPIRETIME` have no side effects (for now on the Redis protocol only: memcache and
  collection reads still read the disk on the I/O thread). When one of them misses the cache, the partial
  reply is dropped and the command stops. The connection writes its batch, sends the earlier replies and asks
  the *read pool* for the key. The wait is asynchronous: the I/O thread serves other connections meanwhile.
  When the key reaches the cache, the command runs again and the pipeline's reply order is kept. A pool of
  `read-threads` threads (64 by default; with 0 the I/O thread reads the disk, as before) does the reads.
- **One read per key.** If several clients ask for the same key while it is being loaded, they all wait for
  the same read (*single flight*). Without this, a hot key that leaves the cache causes a queue of identical
  reads (*cache stampede*).
- **Pipeline in parallel.** When it defers a read, the connection already asks the pool for the keys of the
  following reads in the buffer (up to 256 commands), so the disk reads overlap.
- **Admission.** A key loaded by the pool enters the cache even if the admission filter does not know it,
  because a client is waiting for it.
- **Before deferring, RocksDB's memory.** A read that misses the cache first asks RocksDB whether it can
  answer with what it has in memory only (memtables, block cache and Bloom filters). If it can, the command
  goes on at once, on the I/O thread. This covers keys that do not exist and values larger than
  `cache-max-object-size` whose block is in the block cache, which are not kept in the object cache. `GET` of
  a missing key went from 17k/s to 2 million/s with a pipeline of 16 (300k/s without a pipeline), and `GET` of
  8 KB values from 17k/s to 800k/s. `INFO stats` shows these reads in `memory_reads`.
- **Batches (`read-batch`, off by default).** With `read-batch N` greater than 1, when there are more keys in
  the queue than threads, each thread takes up to N and reads them all with one RocksDB `MultiGet`. That saves
  CPU (index and filter consulted once, keys from the same block read together), but RocksDB reads different
  SST files one after the other, even with io_uring; parallelism across files needs its coroutines, which
  depend on folly. With random keys, which nearly always fall in different files, there was no measurable gain
  (see `bench/RESULTADOS.md`), so the default is 1.

`INFO stats` shows `deferred_reads` (reads deferred), `read_pool_loads` (keys loaded by the pool),
`read_pool_batches` (reads done: one key, or a batch), `read_pool_joined` (requests that joined a read in
progress) and `read_pool_queued`.

**`INFO latency`** shows histograms, in microseconds, of where the time goes: `storage_get_usec` (a RocksDB
read), `storage_multiget_usec` (a `read-batch` batch), `storage_write_usec` (writing a batch),
`key_lock_wait_usec` and `key_read_lock_wait_usec` (waiting for a key lock to write and to read),
`write_batch_hold_usec` (how long a batch holds its locks) and `read_pool_load_usec` (from the request to the
pool until the key is in the cache). Each line has `calls`, `p50`, `p99`, `p99.9`, `p99.99` and `max`. A
percentile is the upper bound of the histogram's bucket (an error of at most 25%). `CONFIG RESETSTAT` resets
the histograms.

## Roadmap

1. **Done:** strings, TTL, RESP2/3, memcache, a memory pool with a cache, and persistence in RocksDB.
2. **Done:** Hash, Set, ZSet and List, with subkeys in the `data` CF and a version in the metadata for O(1)
   `DEL`.
3. **Done:** secondary indexes on Hash (`IDX.*`), written to the `index` CF in the same WriteBatch as the
   data, with background backfill, `UNIQUE` and compound indexes.
   Next steps: early compaction of large collections with many tombstones (small ones are already kept whole
   in the cache).
4. **Done:** the SCAN family, CONFIG SET, CONFIG REWRITE, AUTH and ACL users with permissions per command and
   per key pattern.
   TLS (optional port, client certificates, login by CN, live certificate changes) and ACL LOG.
   Benchmark with memtier against Redis and Kvrocks; disk reads off the I/O threads (read pool, with one read
   per key and pipelines in parallel) and `INFO latency`.
   Next steps: asynchronous disk reads across files (the batched `MultiGet`, already tried, gained nothing
   with random keys), collection reads through the pool, shards per thread and TLS on memcache.
5. **Done:** change feed (`CDC.READ`), decoded from the kept WAL, with `BLOCK` that holds no thread.
   Primary → replica replication (`REPLICAOF`), with full sync by snapshot, the WAL stream, continuing after
   restarts, and promotion.
   JSON type (`JSON.*`, compatible with RedisJSON), with JSONPath and filters, and secondary indexes on JSON
   documents (`IDX.CREATE ... ON JSON`, with `UNIQUE` and compound indexes).
   Multi-valued TAG (a separator in hashes, arrays in JSON) and RediSearch-compatible search
   (`FT.CREATE`/`FT.SEARCH` with TAG and NUMERIC).
   Transactions (`MULTI`/`EXEC`/`WATCH`, with the block isolated by the keys' locks), blocking list and sorted
   set commands (`BLPOP`, `BLMOVE`, `BZPOPMIN`...) that wait without holding a thread, and Pub/Sub with
   channels, patterns and shard channels.
   Operations: consistent online backup (`BACKUP`, and `BGSAVE` with `backup-dir`, through RocksDB
   checkpoints), lock-free readers that never see a write before its commit (nor part of an `EXEC`),
   `SHUTDOWN`, `SLOWLOG`, `MONITOR`, `CLIENT LIST/KILL` of every connection, `OBJECT`, `TOUCH` and
   `MEMORY USAGE`.
   High availability: `WAIT`, TLS to the primary, planned `FAILOVER` and automatic failover through Redis
   Sentinel.
   Lua: `EVAL`/`EVALSHA` and Redis 7 functions (`FUNCTION LOAD`, `FCALL`), with Redis's `redis.*` API,
   `cjson`, atomic scripts (a script has the whole keyspace to itself), `SCRIPT KILL`, and function libraries
   stored in the database and replicated. Without a pipeline, `EVAL` runs as fast as on Redis (~155k per
   second with 50 clients); with a pipeline of 16, `EVAL "return 1"` does 984k per second (Redis: 909k) and an
   `EVAL` with an `INCR` does 359k (Redis without persistence: 587k).
   Next steps: streams; `TEXT` fields and `FT.AGGREGATE`.
6. **Done:** a test on AWS in seven phases ([cloud/](cloud/README.md), results in `bench/results/cloud-*`):
   in memory and larger than memory against Redis and Kvrocks, scaling with cores, high availability with
   Sentinel, crashes and power cuts, and 10 hours of steady load. No acknowledged write was lost to `kill -9`,
   nor to a power cut with `fsync always` (`everysec`: at most the last 0.6 s); a failover loses none of the
   writes acknowledged with `WAIT` and stops them for about 5 s; nothing grew in 10 hours. It found six bugs that
   the unit tests, the sanitizers and the fuzzers had not: one I/O context shared by every thread, the WAL
   sought again for every batch sent to a replica, replication links that `operator||` left hanging, a full sync
   of every replica after each failover, the WAL a syncing replica needed trimmed under it, and a live WAL that
   grew to 10 GB.
   Short versions of the crash and failover phases run in CI (`tests/docker_fault_test.sh`), a check for each
   of those bugs that could come back unseen.
   The CPU per read with more data than memory, 2 to 3 times Kvrocks's in phase 3: most of it went to waking a
   read-pool thread for every key not in the object cache, even when the OS had its block in the page cache.
   Such a read is now served on the I/O thread (`page-cache-reads`, `preadv2` with `RWF_NOWAIT`); in Docker,
   GETs that the page cache serves went from 56–79 to 21 µs of CPU each, and uniform reads of 6 GB through a
   1 GB container from 133–170 to 78–99 µs (Kvrocks 97–99), with 1.7 times the throughput. Not measured in
   the cloud again; there more of the reads reach the disk, and each of those still costs two thread wake-ups.
   The `SENTINEL FAILOVER` window, where the old primary kept taking writes that its other replicas
   acknowledged and the promoted one never got: with `promotion-handoff yes`, `REPLICAOF NO ONE` on a replica
   asks its primary to hand over, as `FAILOVER` does. In Docker, a `SENTINEL FAILOVER` under `WAIT 1` writes lost
   none and nothing synced in full (without it, 14,000 lost and two full syncs); CI runs that test.
   Next steps, from what those tests showed:
   - the larger-than-memory latency curve again (that run's memtier replayed the same keys), and the ~25% of
     CPU the write path leaves idle on 16 vCPUs;
   - a security review (limits, `CONFIG SET` paths), CodeQL and image scanning, more fuzz targets;
   - what the tests did not cover: client libraries' own suites (BullMQ, Sidekiq, redis-py, Redlock), a full or
     failing disk, partitions between clients and server, soaks of weeks, other instance types, and the
     restart time since the live WAL is bounded (phase 6's 8 to 13 s came before).
